### **Автор:** Архитектор Банка "Стандарт"
### **Дата:** 2025-12-10

### **Решение**

#### Архитектурное решение

**1. Микросервисная архитектура для кредитов**

Создаём новый микросервис **Сервис кредитов (Credit Service)** в рамках целевой архитектуры:

**Компоненты:**
- **API Layer** — REST API для подачи заявок, получения предодобренных предложений, проверки статуса
- **Business Logic Layer** — бизнес-правила для кредитов, валидация, оркестрация
- **Integration Layer** — интеграция с Системой скоринга, Кредитным конвейером, АБС, СМС-шлюзом
- **Database (MS SQL)** — хранение заявок, предодобренных предложений, кэш скоринга

**Технологии:**
- .NET Core Web API
- MS SQL Server
- Entity Framework Core
- RabbitMQ для асинхронных операций

**2. Интеграция с системой скоринга**

- **Новые клиенты (через сайт):** Полный скоринг через БКИ при подаче заявки
  - Сервис кредитов → Система скоринга → БКИ
  - Rate limiting: 100 запросов/минуту
  - Timeout: 10 секунд (если БКИ не отвечает → graceful degradation)

- **Существующие клиенты (через интернет-банк):**
  - Предодобренные предложения рассчитываются заранее (batch в ночное время)
  - Результаты кэшируются в MS SQL (TTL 24 часа)
  - При подаче заявки — упрощённый скоринг (ускоренная процедура)

**3. Real-time интеграция с Кредитным конвейером**

**Проблема:** Сейчас batch-обмен раз в сутки → заявки обрабатываются только на следующий день

**Решение:**
- REST API интеграция: `POST /api/v1/credit-applications` в Кредитный конвейер
- Event-driven: Сервис кредитов публикует событие `CreditApplicationCreated` в RabbitMQ
- Кредитный конвейер подписывается на событие, забирает заявку через API
- Обработка в течение рабочего дня (< 4 часов)

**4. СМС-подтверждения**

- Сервис кредитов интегрируется с СМС-шлюзом (существующий, используется для депозитов)
- Двухфакторная аутентификация:
  1. Клиент вводит телефон в форме
  2. Генерируется СМС-код (6 цифр, TTL 5 минут)
  3. Клиент вводит код для подтверждения
  4. После подтверждения заявка создаётся
- СМС-уведомления о статусе заявки (отправка асинхронно через RabbitMQ)

**5. API Gateway и защита**

- **API Gateway (Kong/Nginx)** — единая точка входа для всех запросов
- Rate limiting: 100 запросов/минуту на клиента
- OAuth 2.0/JWT аутентификация для интеграций (кол-центр, интернет-банк)
- TLS 1.2+ для всех каналов

**6. Кэширование и оптимизация**

- **Предодобренные предложения:** Расчёт в ночное время (02:00 МСК), кэш в MS SQL (TTL 24 часа)
- **Результаты скоринга:** Кэш в MS SQL (TTL 30 дней для существующих клиентов)
- **Справочные данные (продукты, ставки):** Redis Cache (TTL 1 час)

**7. Асинхронная обработка**

- **RabbitMQ** для асинхронных операций:
  - Отправка СМС-уведомлений
  - Публикация событий для Кредитного конвейера
  - Логирование и аудит
- Retry policy: 3 попытки с экспоненциальной задержкой при ошибках

**8. Graceful degradation**

- Если БКИ недоступен → заявка сохраняется со статусом "Ожидает проверки", обработка позже
- Если СМС-шлюз недоступен → заявка создаётся, СМС отправится при восстановлении (retry из очереди)
- Если Кредитный конвейер недоступен → заявка сохраняется в MS SQL, синхронизация при восстановлении

### **Альтернативы**

**Альтернатива 1: Расширение монолитного интернет-банка вместо микросервиса**

Добавить функционал кредитов в существующий монолит интернет-банка (ASP.NET MVC 4.5).

**Почему отклонена:**
- Монолит уже имеет проблемы с производительностью и поддерживаемостью
- Усложняет деплой: любое изменение требует перезапуска всего приложения
- Невозможно независимое масштабирование кредитов и депозитов
- Не соответствует целевой архитектуре (микросервисы)
- Технологический долг: старый стек (ASP.NET MVC 4.5), нет поддержки современных библиотек

**Альтернатива 2: Синхронная интеграция с Кредитным конвейером (прямой вызов API)**

При подаче заявки синхронно вызывать API Кредитного конвейера и ждать ответа.

**Почему отклонена:**
- Увеличивает response time подачи заявки (клиент ждёт обработки)
- Кредитный конвейер может быть перегружен (зависимость от его доступности)
- Если Кредитный конвейер недоступен → клиент не может подать заявку
- Нарушает принцип слабой связанности (tight coupling)

**Решение:** Event-driven архитектура через RabbitMQ — заявка создаётся мгновенно, обработка асинхронно.

**Альтернатива 3: Batch-обмен через БД (оставить как есть)**

Продолжить использовать batch-обмен через Oracle БД АБС раз в сутки.

**Почему отклонена:**
- Не соответствует бизнес-требованию: обработка в течение рабочего дня (< 4 часов)
- Клиент получает ответ только на следующий день (плохой UX)
- Прямая работа с БД АБС создаёт tight coupling (изменения в БД АБС ломают интеграцию)
- Нет возможности для real-time уведомлений

**Решение:** REST API + Event-driven для near-real-time обработки.

**Альтернатива 4: Использование Kafka вместо RabbitMQ**

Использовать Kafka для асинхронной обработки.

**Почему отклонена:**
- Текущая платформа интернет-банка (ASP.NET MVC 4.5) несовместима с Kafka
- Требуется обновление платформы (дополнительное время и ресурсы)
- Нет экспертизы в команде по Kafka (требуется обучение)
- RabbitMQ — существующая инфраструктура банка, есть экспертиза

**Решение:** RabbitMQ для MVP, миграция на Kafka — следующий этап (после обновления платформы).

### **Недостатки, ограничения, риски**

**Недостатки:**

1. **Две системы для управления заявками:** Сервис кредитов (новые заявки онлайн) + Кредитный конвейер (обработка всех заявок). Требуется синхронизация данных.
2. **Зависимость от Кредитного конвейера:** Если API Кредитного конвейера недоступен, обработка заявок задерживается (частично митигируется асинхронностью).
3. **Сложность интеграции:** 5 внешних систем (Скоринг, БКИ, Кредитный конвейер, АБС, СМС-шлюз) — каждая может быть точкой отказа.
4. **Дублирование данных:** Заявки хранятся в MS SQL (Сервис кредитов) и в БД Кредитного конвейера. Требуется механизм синхронизации.

**Ограничения:**

1. **Идентификация новых клиентов только в отделении:** 115-ФЗ не позволяет полностью онлайн онбординг. Клиент должен прийти в отделение для завершения оформления кредита.
2. **Rate limiting на систему скоринга:** Не более 100 запросов/минуту. При пиковых нагрузках возможны задержки (митигация: кэширование предодобренных предложений).
3. **Обработка заявок в рабочее время:** Кредитный конвейер работает 09:00-21:00 МСК. Заявки, поданные ночью, обрабатываются утром.
4. **RabbitMQ вместо Kafka:** Ограничение по throughput и масштабируемости. Миграция на Kafka потребует обновления платформы интернет-банка.

**Риски:**

1. **Риск перегрузки системы скоринга**
   - *Вероятность:* Средняя (при запуске рекламной кампании)
   - *Митигация:* Rate limiting (100 req/min), кэширование результатов скоринга (TTL 30 дней), batch-расчёт предодобренных предложений в ночное время

2. **Риск недоступности БКИ**
   - *Вероятность:* Низкая (внешний сервис, SLA 99.5%)
   - *Митигация:* Graceful degradation — заявка сохраняется со статусом "Ожидает проверки БКИ", обработка позже. Timeout 10 секунд, retry policy

3. **Риск дублирования заявок при повторных запросах**
   - *Вероятность:* Средняя (клиент нажимает кнопку "Отправить" несколько раз)
   - *Митигация:* Идемпотентность API — используется уникальный `idempotency-key` (UUID) для каждой заявки. Повторные запросы с тем же ключом возвращают ту же заявку

4. **Риск рассогласования данных между Сервисом кредитов и Кредитным конвейером**
   - *Вероятность:* Средняя (при сбоях интеграции)
   - *Митигация:* Event sourcing — все изменения статуса заявки логируются как события. Reconciliation job (раз в час) проверяет консистентность данных

5. **Риск нарушения SLA 99.9% при росте нагрузки**
   - *Вероятность:* Средняя (органический рост + маркетинг)
   - *Митигация:* Горизонтальное масштабирование (stateless сервисы), автоскейлинг (Kubernetes), мониторинг метрик (Prometheus + Grafana), алерты при превышении thresholds

6. **Риск утечки персональных данных (152-ФЗ)**
   - *Вероятность:* Низкая (при соблюдении мер безопасности)
   - *Митигация:* Шифрование ПДн в БД (AES-256), TLS 1.2+ для всех каналов, OAuth 2.0/JWT для API, логирование доступа, аудит ИБ, penetration testing

7. **Риск низкого конверсия из-за сложного процесса**
   - *Вероятность:* Средняя (новая функциональность, требуется оптимизация)
   - *Митигация:* A/B тестирование форм заявки, аналитика (Google Analytics, Яндекс.Метрика), user feedback, постоянная оптимизация UX

**Метрики успеха:**

- ✅ Response time API < 500 мс (95-й перцентиль)
- ✅ Обработка заявок < 4 часов (99% заявок)
- ✅ Uptime 99.9% (< 8.76 часов downtime в год)
- ✅ Конверсия заявок > 10% (от просмотра формы до подачи)
- ✅ Доля одобренных заявок > 40% (после скоринга)
- ✅ Снижение нагрузки на кол-центр на 30% (благодаря информативным статусам)
