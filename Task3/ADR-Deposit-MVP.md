# ADR: Концептуальная архитектура MVP открытия депозитов

### **Название задачи:** Онлайн подача заявок на депозиты (MVP)

### **Автор:** Команда цифровой трансформации банка "Стандарт"

### **Дата:** 09.12.2025

---

## **Функциональные требования**

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| 1 | Новый клиент, Сайт, Кол-центр | Подача заявки через сайт | 1. Клиент открывает сайт банка и просматривает депозиты с актуальными ставками<br/>2. Заполняет форму: ФИО, телефон, выбирает депозит<br/>3. Отправляет заявку<br/>4. Система создает заявку и передает в кол-центр<br/>5. Менеджер кол-центра звонит клиенту, обсуждает условия<br/>6. Клиент приходит в отделение для идентификации и открытия депозита |
| 2 | Существующий клиент, Интернет-банк | Подача заявки через интернет-банк | 1. Клиент входит в интернет-банк (аутентификация)<br/>2. Просматривает депозиты с персонализированными ставками<br/>3. Указывает счет списания и сумму, подтверждает СМС-кодом<br/>4. Система создает заявку и передает в бэк-офис<br/>5. Клиент получает СМС-уведомление о статусе |
| 3 | Менеджер бэк-офиса, АБС | Обработка заявки (MVP) | 1. Менеджер видит заявку в АБС<br/>2. Проверяет данные клиента и условия<br/>3. Подтверждает ставку (СМС клиенту)<br/>4. Утверждает открытие депозита в АБС<br/>5. АБС создает депозитный счет<br/>6. Клиент получает СМС об открытии |
| 4 | Менеджеры депозитов и кредитования | Управление ставками | 1. Менеджер кредитования определяет базовые ставки на основе ставки ЦБ РФ и кредитного риска<br/>2. Вносит ставки в систему (замена Excel)<br/>3. Менеджер депозитов корректирует при необходимости<br/>4. Система кэширует ставки<br/>5. Ставки отображаются на сайте и в интернет-банке в реальном времени |

## **Нефункциональные требования**

| **№** | **Требование** |
| :-: | :- |
| 1 | **Производительность:** Отклик UI < 100 мс, API < 500 мс. Загрузка ставок < 1 сек через кэширование |
| 2 | **Надежность:** Uptime 99.9% (24/7). Отказоустойчивость при сбое ЦОД |
| 3 | **Защита АБС:** Избежать прямой работы с АБС. API Gateway с rate limiting и буферизацией |
| 4 | **Безопасность:** Шифрование TLS 1.2+, СМС-подтверждение, логирование для аудита |
| 5 | **Масштабируемость:** Горизонтальное масштабирование микросервисов. Stateless сервисы |
| 6 | **Технологии:** Использование существующих технологий банка (MS SQL, .NET, Oracle) |
| 7 | **Поддерживаемость:** Микросервисная архитектура (начать с депозитов). Модульность |
| 8 | **Интеграция:** Интеграция с АБС без модификации legacy-кода (только через API-слой) |
| 9 | **Транзакционность:** Гарантия целостности данных при создании заявки |
| 10 | **Регуляторные требования:** Соответствие ЦБ РФ. Идентификация новых клиентов в отделении (115-ФЗ) |

## **Решение**

### Диаграммы архитектуры

Решение представлено диаграммами C4:
- **C4-Context-Diagram** (drawio и puml) - контекст системы
- **C4-Container-Diagram** (drawio и puml) - детализация интернет-банка и АБС

### Архитектурное решение

#### 1. Общая концепция

**Микросервисная архитектура** с постепенной миграцией от монолита. Создание нового слоя микросервисов для депозитов, работающего параллельно с существующим монолитом.

#### 2. Ключевые компоненты

**A. Канальный уровень**
- **Веб-сайт** (PHP + React.js) - для новых клиентов
- **Web Application** (React.js SPA) - новый фронтенд интернет-банка

**B. API Gateway** (Kong / Nginx)
- Единая точка входа для всех запросов
- Rate limiting - защита АБС от перегрузки
- Аутентификация (JWT), маршрутизация, логирование
- TLS termination

**C. Микросервисы (.NET Core)**
1. **Deposit Service** - управление заявками, валидация, бизнес-правила
2. **Rates Service** - управление ставками (замена Excel), кэширование
3. **Notification Service** - СМС и Email через очереди (асинхронно)
4. **Integration Service** - единственная точка интеграции с АБС

**D. Инфраструктура**
1. **Redis Cache** - кэширование ставок и справочных данных (решает проблему медленной загрузки >1 сек)
2. **RabbitMQ** - асинхронная обработка уведомлений (не блокирует основной flow)
3. **Deposits DB (MS SQL)** - отдельная БД для заявок (снижает нагрузку на БД АБС)

**E. Модернизация АБС**
1. **ABS API Layer (REST)** - новый фасад для legacy-логики (без модификации Delphi-кода)
2. **ABS Core Logic** (Delphi + PL/SQL) - без изменений
3. **Backoffice Web UI** - интерфейс для менеджеров

#### 3. Логика принятия решений

**Почему микросервисы?**
- Монолит (ASP.NET MVC 4.5) устарел, зависимость от подрядчика
- Постепенная миграция без "big bang"
- Независимое масштабирование компонентов

**Почему API Gateway?**
- Защита перегруженной БД АБС (критическое требование)
- Rate limiting предотвращает перегрузку
- Централизованная безопасность и мониторинг

**Почему отдельная Deposits DB?**
- Снижение нагрузки на критичную БД АБС
- Независимая схема, оптимизированная под заявки

**Почему Redis?**
- Решает проблему медленной загрузки (>1 сек → <100 мс)
- Ставки меняются редко, TTL для инвалидации

**Почему RabbitMQ, а не Kafka?**
- Текущая версия интернет-банка несовместима с Kafka
- RabbitMQ достаточно для асинхронных уведомлений
- Миграция на Kafka - на следующем этапе

**Почему не модифицируем АБС?**
- Legacy на Delphi - высокий риск, отсутствие экспертизы
- Создание API-слоя безопаснее и дешевле

#### 4. Технологический стек

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Frontend | React.js SPA | Современный, быстрый |
| API Gateway | Kong / Nginx | Проверенные решения |
| Микросервисы | .NET Core | Экспертиза банка |
| Cache | Redis | Industry standard |
| Message Queue | RabbitMQ | Совместимость |
| DB (новая) | MS SQL | Лицензии банка |
| ABS API | REST (.NET/Java) | На выбор команды АБС |
| Мониторинг | Grafana + Prometheus | Open source |

#### 5. IT-команды

| Команда | Ответственность |
|---------|-----------------|
| Цифровая трансформация (10 чел.) | Координация, архитектура |
| Интернет-банк (10+10 подрядчик) | React фронтенд, микросервисы |
| АБС (20 чел.) | ABS API Layer, интеграция |
| DevOps | API Gateway, Redis, RabbitMQ, мониторинг |
| QA | Интеграционное и нагрузочное тестирование |

#### 6. Обеспечение нефункциональных требований

| Требование | Решение |
|------------|---------|
| Производительность < 100 мс | Redis кэширование, CDN, оптимизация запросов |
| Uptime 99.9% | Репликация Redis, failover, мониторинг Grafana |
| Защита АБС | API Gateway с rate limiting, Integration Service |
| Безопасность TLS | TLS termination на API Gateway, HTTPS везде |
| Масштабируемость | Stateless микросервисы, балансировщик |
| Транзакционность | Saga pattern, компенсирующие транзакции |

## **Альтернативы**

### 1. Модернизация монолита

**Описание:** Добавить функционал депозитов в существующий монолит (ASP.NET MVC 4.5)

**Отклонено:**
- ❌ Усиление зависимости от подрядчика
- ❌ Монолит становится еще сложнее
- ❌ Невозможность независимого масштабирования
- ❌ Устаревший стек (2012 год)
- ❌ Противоречит стратегии цифровой трансформации

### 2. "Big Bang" миграция всего интернет-банка

**Описание:** Полная замена интернет-банка сразу

**Отклонено:**
- ❌ Огромные риски (если что-то пойдет не так, клиенты без обслуживания)
- ❌ Длительные сроки (год+), большой бюджет
- ❌ Невозможность быстрых итераций и обучения

### 3. Прямая интеграция с БД АБС

**Описание:** Микросервисы обращаются напрямую к БД АБС (Oracle)

**Отклонено:**
- ❌ **Критично:** БД АБС уже перегружена
- ❌ Нарушение инкапсуляции
- ❌ Риск нарушения целостности данных
- ❌ Нарушает требование №3 (защита АБС)

### 4. Kafka вместо RabbitMQ

**Описание:** Использовать Apache Kafka для асинхронной обработки

**Отклонено для MVP:**
- ❌ Текущая платформа интернет-банка несовместима с Kafka
- ❌ Требуется обновление платформы
- ✅ **Запланировано на следующий этап** при обновлении платформы

## **Недостатки, ограничения, риски**

### Недостатки

1. **Усложнение архитектуры** - больше компонентов (микросервисы, Redis, RabbitMQ, API Gateway)
2. **Дублирование данных** - Deposits DB дублирует часть данных из АБС, нужна синхронизация
3. **Latency** - больше сетевых вызовов между сервисами
4. **Сложность транзакций** - распределенные транзакции через Saga pattern

### Ограничения

1. **Новые клиенты в отделении** - регуляторное требование 115-ФЗ (идентификация)
2. **MVP с ручной обработкой** - менеджеры бэк-офиса обрабатывают заявки (автоматизация - на следующем этапе)
3. **Зависимость от АБС** - если АБС недоступна, процесс блокируется (нужны retry и graceful degradation)
4. **RabbitMQ временно** - миграция на Kafka потребуется в будущем

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Перегрузка АБС | Высокая | Критичное | API Gateway с rate limiting, кэширование Redis, Integration Service |
| Нет экспертизы в микросервисах | Средняя | Высокое | Обучение команды, консультанты, постепенная миграция |
| Проблемы синхронизации данных | Средняя | Высокое | Event-driven, мониторинг расхождений, reconciliation |
| Отказ критичных компонентов | Низкая | Критичное | Репликация, failover, health checks |
| Расхождение Deposits DB и АБС | Средняя | Высокое | Ночная сверка, алерты, АБС - источник истины |
| Низкая производительность | Средняя | Среднее | Нагрузочное тестирование, кэширование, CDN |
| Превышение бюджета/сроков | Средняя | Высокое | Agile, итерации, MVP с минимальным функционалом |

### Технический долг

1. RabbitMQ → Kafka (после обновления платформы)
2. Монолитный интернет-банк (постепенная декомпозиция)
3. Прямой доступ к БД АБС в некоторых местах (заменить на API)
4. Legacy АБС на Delphi (долгосрочная стратегия замены)

### Метрики успеха MVP

| Метрика | Целевое значение |
|---------|------------------|
| Время подачи заявки | < 3 минуты |
| Доля успешных заявок | > 95% |
| Response time API (p95) | < 500 мс |
| Uptime системы | > 99.9% |
| Заявок через онлайн | 100+ в месяц |
| NPS (удовлетворенность) | > 50 |
| Снижение нагрузки на БД АБС | -30% |

## Заключение

Предложенная архитектура обеспечивает:
- ✅ Защиту АБС через API Gateway и кэширование
- ✅ Постепенную миграцию от монолита
- ✅ Высокую производительность (< 100 мс UI, < 500 мс API)
- ✅ Масштабируемость и отказоустойчивость
- ✅ Соответствие регуляторным требованиям

Решение балансирует между **быстрым выводом MVP** и **стратегической целью цифровой трансформации**.
